=== 3 · THE ARM THAT MEASURED NOTHING, kept because it is the finding ======

Two further loads were run at the same two windows with `--extra "--spec-type
ngram-mod -c N"`, intended as the no-MTP control. They returned GTT 37.77 and
52.16 — byte-identical to the two points above.

That identity is what exposed them. `--spec-type` ACCUMULATES in llama.cpp
(common/arg.cpp uses push_back), so the flag did not replace the profile's
`draft-mtp,ngram-mod`, it appended to it; both "control" loads still ran the
MTP head, and the server log says so in as many words: `creating MTP draft
context against the target model` appears in all four loads. The behaviour is
registered in setup/defects.json and was walked into anyway.

So there is no no-MTP memory point here. It cannot be produced with --extra at
all — a genuine control needs argv that never names draft-mtp, which is what
bench/variants/glm47flash.json's nospec and ngram cells provide. Recorded, not
repaired, because the sweep answers it as a by-product.

WHAT IT WOULD HAVE TESTED, and still open: the derivation from the config says
52.9 KiB/token, the measurement says 110.0, and the factor is almost exactly
two. "The MTP draft context allocates a second full-size KV" is the obvious
hypothesis and it is NOT established — the same two-point pair at the same
windows without the head is what would settle it.

THE ARITHMETIC, and it answers the question section 3 left open:

    no speculation    33.00 -> 40.20   =  55.02 KiB/token   base 29.56 / 29.56
    draft-mtp,ngram   37.77 -> 52.16   = 109.97 KiB/token   base 30.90 / 30.90

EXACTLY DOUBLE. The MTP draft context allocates a second, full-size KV cache.
Each pair agrees with itself on the base to two decimals, which is the check.

And the derivation from the config — 52.9 KiB/token, from MLA's single K
buffer over 47 layers — is 4 % under the no-MTP measurement, not 52 % under
anything. It was never wrong about the model; it assumed one KV cache.
